# e203_exu_alu 验证需求与规划

## 1. 验证目标理解

`e203_exu_alu` 是 E203 处理器执行单元中的关键模块，负责：

- 常规 ALU 算术与逻辑运算
- 分支跳转相关的比较、跳转结果与提交信息
- AGU 访存地址生成、访存握手与异常上报
- CSR 访问控制与写回
- 可选的 MUL/DIV 长流水与 NICE 扩展握手
- 顶层提交、写回、flush 协同

本次验证的核心目标不是修复设计，而是通过接口级验证确认模块在正常路径、边界条件、异常场景和握手背压场景下的行为是否符合规格；若发现失败，应优先视为潜在设计缺陷并进行记录和分析。

## 2. 主要输入输出与观测面

### 2.1 输入侧

- 发射侧握手与上下文：`i_valid`、`i_ready`、`i_itag`、`i_pc`、`i_instr`、`i_pc_vld`
- 操作数与译码信息：`i_rs1`、`i_rs2`、`i_imm`、`i_info`
- 写回相关输入：`i_rdidx`、`i_rdwen`
- 异常与控制输入：`i_ilegl`、`i_buserr`、`i_misalgn`、`flush_req`、`flush_pulse`
- 外围协同输入：`oitf_empty`、`mdv_nob2b`、`cmt_o_ready`、`wbck_o_ready`
- CSR/LSU/NICE 返回侧输入：`csr_access_ilgl`、`read_csr_dat`、`agu_icb_*rsp*`、`nice_*ready/rdata/*`

### 2.2 输出侧

- 发射反馈：`i_ready`、`i_longpipe`、`amo_wait`
- 提交通道：`cmt_o_valid` 及其携带的 PC、指令、异常、分支、访存类信息
- 写回通道：`wbck_o_valid`、`wbck_o_wdat`、`wbck_o_rdidx`
- CSR 请求：`csr_ena`、`csr_wr_en`、`csr_rd_en`、`csr_idx`、`wbck_csr_dat`
- AGU/LSU 请求：`agu_icb_cmd_*`
- 可选 NICE/CSR_NICE 接口输出

### 2.3 可观测原则

- 仅通过顶层输入输出端口进行验证
- 不依赖内部信号判断功能正确性
- 所有时序行为统一通过 Step 接口驱动

## 3. 待验证功能范围

### 3.1 基础功能类

- ALU 常规算术、逻辑、比较、移位、立即数类运算
- 分支/跳转比较结果、写回结果与提交属性
- CSR 读写请求生成与 CSR 非法访问反馈
- Load/Store/AMO 地址生成与 ICB 握手
- 写回与提交路径的数据一致性

### 3.2 控制与协同类

- `valid/ready` 背压处理
- `flush_req` / `flush_pulse` 对进行中事务的影响
- 长流水标记 `i_longpipe`
- `amo_wait` 与 `oitf_empty`、LSU 响应之间的联动
- `mdv_nob2b` 对 MUL/DIV 发射行为的限制

### 3.3 异常与边界类

- 非法指令、访存错位、总线错误上报
- CSR 非法访问错误路径
- 分支比较中的有符号/无符号边界
- 访存地址边界、对齐边界、字节掩码边界
- 写回关闭、提交阻塞、响应延迟、可选接口关闭时的行为

## 4. 主要风险点识别

### 4.1 协议风险

- 顶层同时汇聚多个子模块结果，容易出现 `valid/ready` 互斥或优先级错误
- 提交与写回通道可能在背压条件下出现丢包、重复提交或数据保持错误
- LSU/CSR/NICE 等跨模块握手可能存在 ready 依赖环或响应窗口错误

### 4.2 功能风险

- 分支比较的有符号/无符号判断容易出错
- JAL/JALR/分支类提交信息与写回返回地址可能不一致
- CSR 读改写路径中 `rdwen`、`csr_wr_en`、`csr_rd_en` 组合容易遗漏
- AGU 地址生成、AMO 计算、掩码和异常上报路径复杂，最容易隐藏缺陷

### 4.3 时序与控制风险

- `flush_req` / `flush_pulse` 对正在握手或等待返回的事务处理复杂
- `amo_wait`、`i_longpipe`、`wbck_o_valid`、`cmt_o_valid` 之间存在阶段性联动风险
- 可选功能宏打开或关闭时，接口行为可能不一致

## 5. 验证方法规划

### 5.1 文档与源码分析阶段

- 先阅读顶层接口说明、Python 封装、Guide_Doc 标准文档
- 再阅读 RTL 顶层与关键子模块源码，形成功能分组、功能点和检查点
- 基于源码执行静态缺陷审查，优先发现高风险逻辑缺陷

### 5.2 验证基础设施阶段

- 搭建 DUT 创建函数与 `pytest` fixture
- 为顶层端口设计 bundle 与 env
- 封装基础 API，屏蔽底层握手细节，统一以 Step 驱动
- 构建功能覆盖模型，确保每个功能点和检查点都有可追踪映射

### 5.3 定向测试阶段

- 先完成 API 自测，确保基础驱动可信
- 按功能组实现模板与正式测试
- 优先覆盖静态分析发现的高/中置信度潜在缺陷
- 对失败用例做源码级缺陷分析，形成动态 Bug 文档

### 5.4 收敛阶段

- 对静态分析 Bug 建立动态验证关联
- 检查功能覆盖与行覆盖缺口
- 补充随机测试以增强组合场景覆盖
- 汇总验证结论、缺陷分布与残余风险

## 6. 阶段性交付策略

后续阶段将按如下顺序推进：

1. 形成 DUT 基本信息文档，明确端口和电路类型
2. 建立功能分组、功能点、检测点文档
3. 完成 RTL 静态 Bug 分析
4. 搭建 DUT/Env/API/覆盖率基础设施
5. 生成测试模板并逐批实现定向测试
6. 对发现的 Bug 进行动态关联验证与总结

## 8. 当前阶段结论

第 1 阶段的结论是：`e203_exu_alu` 属于带时钟与复位、含多类子功能与多外设接口握手的复杂时序模块，验证必须围绕“顶层端口可观测行为 + 分阶段覆盖收敛 + 失败优先归因设计缺陷”的方法展开。后续重点风险将集中在握手协议、异常路径、分支比较、CSR 控制、AGU/AMO 地址与数据路径，以及 flush/长流水协同上。
